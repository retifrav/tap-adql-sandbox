# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A desktop GUI ([Dear PyGui](https://pypi.org/project/dearpygui/)) for running ADQL queries against TAP services through PyVO, plus a SIMBAD ID lookup window through astroquery. It is published on PyPI as `tap-adql-sandbox`, and the console entry point is `tap_adql_sandbox.__main__:main`. There are no tests.

## Commands

**Before changing lint, type-check or build commands, read `.claude/notes/tooling.md`**: it holds the measurements behind the rules below.

- Lint: `ruff check`, run from the repo root. Its config is `[tool.ruff]` in `pyproject.toml`: `target-version = "py312"` plus ruff's own default rule set, which is deliberately not pinned, with only `BLE001` ignored (the GUI catches any exception from PyVO, astroquery or Dear PyGui to show it in the window). When an image bump brings a ruff with new default rules, fix the new findings instead of ignoring them or pinning the old set.
- Never run `ruff format`: the code isn't ruff-formatted, and it would rewrite most files.
- Type check: `ty check`, run from the repo root. Its config is `[tool.ty]` in `pyproject.toml`: `python-version = "3.12"`, and `allowed-unresolved-imports`, which lists a glob for every third-party module the code imports plus `setuptools` for `setup.py`. That is what lets it run in the container, where none of them is installed, so an import of a new dependency needs a glob there or ty fails with `unresolved-import`. mypy has been dropped (the `[mypy]` section in `setup.cfg` is gone); don't reintroduce it.
- Build: `uv build --out-dir <scratchpad>/dist`. `dist/` in the tree is gitignored and holds the user's own builds, named after whatever version they last built, so don't build into it: a build of the same version would overwrite theirs. The README's documented routes are `pip install ./` and `python -m build`.
- Publish: the user builds the release locally and uploads it with twine, so PyPI lists its files without provenance (PEP 740 attestations). PyPI accepts those only from Trusted Publishing on GitHub Actions, GitLab CI or Google Cloud, and on 2026-11-22 the user decided not to depend on such third-party infrastructure. So don't propose Trusted Publishing, `pypa/gh-action-pypi-publish` or a publishing workflow until PyPI accepts provenance made locally (the way the user signs Docker images with cosign and their own key pair) or from self-hosted CI such as TeamCity. **Before bringing provenance up again, read the Publishing and provenance section of `.claude/notes/tooling.md`**, which has what PyPI accepts and the warehouse issues to watch.
- Smoke-run in the container: `uv run --isolated --no-project --with <built .whl> tap-adql-sandbox --version` (or `--help`). All dependencies install on arm64 (verified; x86_64 untested), and every module is imported before argparse runs, so this also proves the imports work. It needs PyPI, which is sometimes unreachable from the container. The container has no display, but Xvfb and Mesa are installed (verified on x86_64), so the real GUI can run on a virtual one and save its frames to PNG. The recipe is in `.claude/notes/dearpygui.md`, and it includes the `-noreset` that Xvfb needs.
- `uv run --with .` also works, but setuptools leaves an in-tree `build/` behind. Delete it afterwards.
- License metadata is the SPDX expression `license_expression = GPL-3.0-or-later` in `setup.cfg`'s `[metadata]` (PEP 639), so there is no `License ::` classifier. Don't add one back: setuptools deprecates them, and next to an expression it refuses to build at all. `license_expression` needs `setuptools>=77` in `[build-system]`, so don't lower that floor. `-or-later` is the user's decision, even though the old classifier was the plain `GPLv3` one rather than `GPLv3+`. Switching to `-only` would change the licensing terms, so ask first. **Read the License metadata section of `.claude/notes/tooling.md` first.**

## Architecture

- `__main__.py` builds the entire UI imperatively inside `main()`: the menu bar, main window, save-file dialog, Donation window, About window, theme bindings, handler registries and viewport. It also holds the query callbacks. `simbad.py` builds the SIMBAD window and its callback, `examples.py` is pure data, `theme.py` has the font and theme factories, `scaling.py` detects the display's content scale and has `scaled()`, `config.py` holds runtime settings, `mirrors.py` has the fallback to mirror servers, and `__init__.py` defines `applicationPath` and `settingsFile`.
- Widgets are addressed by **string tags**, not by references. Callbacks reach them with `dpg.get_value("errorMessage")`, `dpg.show_item("resultsGroup")` and so on, and theme bindings at the end of `main()` use the same tags. So renaming a tag means grepping both `__main__.py` and `simbad.py`. The SIMBAD window uses `…SimbadIDs`-suffixed tags. The `"cell-handler"` item handler registry (right-click copies a cell) is created in `main()` and shared by both results tables.
- The Donation window (`donationWindow`, Help → Donation) shows `sponsorsURL`, `donationSignedURL` and `donationWallets` from `__main__.py`, which duplicate the README's Donation section, so change the two together. Wallet addresses are flat buttons (`getCopyableTheme`) copied on **left** click by `walletAddressClicked`, unlike table cells, which copy on right click. The label turns into a yellow `[copied]` for 1 s, left-aligned with `str.ljust` to the address length so it starts where the address does and the button keeps its width (the font is monospaced; trailing spaces count in a label's width). The two themes are created once with the window and passed in through `user_data`, so a click creates no theme items. The address text is grey (`styleCopyableTextColor`), darker than the default white. The rows are in a group bound to `getCompactListTheme()`, which gives the texts and the buttons the same smaller `FramePadding.y` (`styleCompactListFramePadding`, 3) and no `ItemSpacing.y`, so the rows are 30 px apart instead of 42. Change the vertical padding only through that theme, never on the buttons alone: a text before a button in a horizontal group lines up with the button's label only while both have the same `FramePadding.y`, and zero padding on the button alone put the address about 6 px above its `XLM:`. The theme is still in effect when the list's group ends, so the plain `add_spacer()` after the list is what puts the item spacing back before "Signed variant". The currency names are bold. Dear PyGui has no bold style, so that is a second font, `getBoldFont()`, loaded once with the window and bound with `bind_item_font` to a text of its own, between `"- "` and `":"` texts in a `horizontal_spacing=0` group. **Before adding another weight or bold text elsewhere, read the Fonts section of `.claude/notes/dearpygui.md`.**
- Text layout: Dear PyGui gives every standalone text `FramePadding.y` above and below, so separate text items never sit as close as the lines of one multiline text. A paragraph with a hyperlink inside it (the Donation window's first one) is therefore a group bound to `getInlineTheme()` (no frame padding, no item spacing; the texts carry their own spaces), starting with a `styleFramePadding[1]` spacer, with its lines broken by hand at the window width like the About window's `\n`-broken first paragraph. Dear ImGui can't flow text around a button, so such a paragraph can't wrap by itself. **Before changing either theme or that layout, read the Text layout section of `.claude/notes/dearpygui.md`**, which has the measurements.
- Both lookup flows (`executeQuery`, `getSimbadIDs`) follow the same sequence:
  1. Hide previous results and errors, and show the loading indicator.
  2. Validate the input.
  3. Query.
  4. Delete the results table and rebuild it from scratch under its group parent.
  5. Restore the button.

  Every early `return` must restore the button and indicator state: `showLoading(False)` in the main window, a manual hide/show pair in `simbad.py`.
- `config` is mutable module state, overwritten from the CLI arguments in `main()` after import. Always use `from . import config` and read `config.debugMode` at call time. `from .config import debugMode` would freeze the default.
- HiDPI: Dear PyGui scales nothing on GNU/Linux, so the app does it itself, following Dear ImGui's own GLFW example. **Before changing the scaling, or when bumping Dear PyGui, read the HiDPI section of `.claude/notes/dearpygui.md`.**
  - `main()` sets `config.uiScale` before any UI is created. It comes from `--ui-scale`, or else from `scaling.getContentScale()`. That function returns `Xft.dpi / 96` on Linux, read through Dear PyGui's own bundled GLFW via `ctypes`, and 1 on other platforms, because macOS and Windows scale the window themselves.
  - Every size in pixels handed to Dear PyGui goes through `scaled()`: the font size, theme style values, the viewport size and minimum, widget `width`/`height`/`min_size`/`indent`, spacer heights, and pixel thresholds compared with item sizes (the 150 px per column check in `executeQuery`).
  - Not scaled: `-1` widths, table column weights, and the loading indicator's `radius`, which is measured in text line heights.
  - A Dear ImGui style size that the theme doesn't set stays at its unscaled default. When the UI starts relying on one, add it to the theme through `scaled()`, with its default value. That's why `CellPadding` is there.
- The query path is `pyvo.dal.TAPService(url, session=addConnectTimeout(create_session())).search(query)`, called through `tryMirrors` → `results.to_table().to_pandas()`. The result goes into the module global `lastQueryResults`, which is what "Save results to pickle" writes. A guard refuses to render a result whose column count plus the `#` enumeration column (shown unless `--no-enum-column` or a single row, `addEnumerationColumn`) exceeds `config.dpgColumnsMax` (511), because Dear ImGui asserts `columns_count < IMGUI_TABLE_MAX_COLUMNS` (512) in `BeginTable` (issues #8, #14 were the 64-column limit of Dear PyGui 1.x).
- A failed query shows `str(ex)`, plus the text from `getFirewallBlockHint(ex)` when that is not empty. It is only for a Cloudflare WAF block page: a `DALServiceError` with `code == 403` whose `ex.cause.response` has `Server: cloudflare` and a `text/html` content type, and it ends with the `CF-RAY` header. Don't key it on the `Server` header alone, because Cloudflare proxies every response from such a host, a 200 and the service's own VOTable errors included. PyVO keeps the body only for `text/plain` errors, so without the hint the user sees a bare `403 Client Error: Forbidden`.
- The SIMBAD lookup uses `Simbad.query_objectids`, called through `tryMirrors` with `Simbad.server` set per attempt (`querySimbadIDs`). The ID column is `ID` before astroquery 0.4.8 and `id` from 0.4.8 on, and both cases are handled deliberately.
- Mirror fallback exists because CDS (SIMBAD's main server) has been offline since late October 2026 after a security incident. Nothing in the code has to change when CDS is back, because it is tried first anyway, but the README's Known problems section, which documents the outage for users, will need updating then. **Before changing it, read `.claude/notes/simbad.md`**, which has the evidence behind these rules:
  - `tryMirrors(servers, attempt)` calls `attempt` with each server in turn. The first one is the main server, and it is tried first on **every** call, never skipped after a failure, so the app recovers by itself once CDS is back. That's the user's decision; don't cache the working mirror.
  - Only `unavailableErrors` (`DALProtocolError`, `OSError`) move on to the next server. PyVO raises `DALServiceError` for HTTP errors and `DALFormatError` for a connection error or timeout in a query, and both subclass `DALProtocolError`. `OSError` covers raw `requests` errors, since `RequestException` subclasses it, so don't import `requests` for catching them. It is imported only for the connect timeout's adapter. `DALQueryError` (a bad query, which SIMBAD returns as HTTP 400 with an ERROR VOTable) is not retried, because every mirror would fail the same way.
  - The last server's error propagates unchanged into the existing error display, so a single-server list behaves as a plain call. Every fallback is logged to stdout, visible without `--debug`: a WARNING for each failed server and an INFO naming the mirror that answered. The user asked for that.
  - The main server gets `config.mainServerConnectTimeout` (5 s) to accept the connection, but only when mirrors follow it. CDS no longer answers with a fast 404: it drops connections, and PyVO and astroquery set no timeout, so each attempt waited out the OS connect timeout (136 s measured). Limiting only the main server, and not the mirrors, is the user's decision on 2026-11-22, so don't extend it to mirrors unasked. It is a connect timeout only, a `(connect, None)` pair. Never add a read timeout: it would cut off a slow query on a working server and send it again to a mirror. Mechanism: `tryMirrors` sets the `attemptConnectTimeout` ContextVar around the main server's attempt, and `ConnectTimeoutAdapter` applies it to requests that have no timeout of their own. `addConnectTimeout()` mounts that adapter on PyVO's per-query session (`create_session()` from `pyvo.utils.http`, which keeps PyVO's User-Agent) and once, at import, on astroquery's private `Simbad._session`, which `Simbad.tap` hands to its `TAPService`. astroquery has no public network timeout: `Simbad.timeout` is the server-side limit for async jobs. A session without the adapter gets no timeout, so a new query path has to go through `addConnectTimeout()`. `requests` is in `install_requires` and in ty's globs for that import.
  - TAP queries get mirrors only from `getTapServiceMirrors`, when the service field equals a `tapServices` URL (trailing `/` ignored). A URL the user typed is never redirected, and the field is never rewritten to the mirror.
  - The SIMBAD window's server list is `conf.server` and then the rest of `conf.servers_list`, from `astroquery.simbad`. The `Simbad.server` setter rejects any name not in that list, so never hard-code host names there. Released astroquery (0.4.11) lists `simbad.harvard.edu`, not `simbad.cfa.harvard.edu`, and has no IDIA yet.
- `examples.py` holds `tapServices`: service key → `name`, `url`, optional `mirrors` (a list of URLs, tried in order by `tryMirrors`) and `examples` (a list of `{description, query}`). A `url` is the TAP service's base URL, never `…/sync`: PyVO appends `/sync` itself, which is how the old SIMBAD URL ended up requesting `…/sim-tap/sync/sync`. The Help → Examples submenus are generated from it in insertion order. The query prefilled at startup is picked **by position**, `tapServices["padc"]["examples"][5]`, so inserting or reordering PADC examples silently changes it.
- NASA Exoplanet Archive examples (`tapServices["nasa"]`) must get past both Cloudflare's WAF in front of the archive and the archive's own query checks, so they must not contain any of these: a string literal followed by `AND`/`OR` and then `<column> IS [NOT] NULL` (put the literal condition last, or write `NOT x IS NULL`), a subquery, `WITH`, or `AS` before a table alias (the backend is Oracle and gets the query untranslated, so `FROM ps a`, never `FROM ps AS a`). Re-run every NASA example against `…/TAP/sync` after changing one. **Before changing them, read `.claude/notes/nasa-exoplanet-archive.md`**, which has the measurements and the rewrites that failed.
- The UI font is JetBrains Mono **Thin** (`getGlobalFont()`), and `getBoldFont()` loads its Bold. Thin is the user's decision: on 2026-11-22 they tried Regular across the whole application and found all the text too bold, so don't switch the UI font to a heavier weight without asking. Both files in `fonts/` come from the same JetBrains Mono release, 2.304 (the latest on 2026-11-22), so update them together. **Before changing a font file, read the Fonts section of `.claude/notes/dearpygui.md`.**
- Fonts and icons are loaded relative to `applicationPath`, and they reach the wheel only through the `graft` lines in `MANIFEST.in` plus `include_package_data=True` in `setup.py`. A new resource directory needs its own `MANIFEST.in` line.
- Dear PyGui `>= 2.3` is required (`install_requires`), so there are no Dear PyGui version branches. **Before changing that minimum or the key handling, read `.claude/notes/dearpygui.md`**, which has the evidence behind these rules:
  - Key handling: use `dpg.mvKey_*` constants, never raw key numbers. Since 2.0 they are Dear ImGui `ImGuiKey` values (named keys start at 512), and Dear ImGui rejects anything else. `mvKey_LWin`/`mvKey_RWin` still hold 1.x values and are just as invalid. For modifiers, use `mvKey_ModCtrl`/`mvKey_ModSuper`/`mvKey_ModShift`/`mvKey_ModAlt`. On macOS Dear ImGui swaps Ctrl and Cmd, so there `mvKey_ModCtrl` is Cmd and `mvKey_ModSuper` is the physical Ctrl key.
  - The Cmd/Ctrl + R shortcut: a single key-press handler on `mvKey_R`, with `keyPressCallback` checking `dpg.is_key_down(dpg.mvKey_ModCtrl)`. Dear ImGui reports Cmd as Ctrl on macOS, so that one check is Cmd + R there and Ctrl + R elsewhere.
  - Pass `tag=`, never `id=`, which warns `id keyword renamed to tag`.
  - Don't add font range hints. Glyphs load on demand since 2.3, `add_font_range_hint` is a no-op, and its deprecation decorator rewrites the process-wide `warnings` filters.
  - `hint` does nothing on multiline inputs (Dear PyGui clears it).
  - `wrap=0` on a text wraps at the window edge.
  - Loading indicators: pass `style=dpg.mvLoadInd_Ring` (or `mvLoadInd_DottedCircle`), never a raw number. `0` and `1` are the pre-2.3 drawings, which Dear PyGui keeps for compatibility. `1` is the ring whose tail jerks at the end of every cycle, and it ignores `speed`. The new ring is `radius` line heights across, smaller than the old one at the same `radius`. That is why `radius`, `thickness` and `indent` were retuned to keep the old outline.
  - Lowering the minimum would bring back version branches for all of the above, and Intel Macs would need one, since macOS x86_64 wheels stop at 2.1.1. Ask first.
- The query input (`queryTextID`) is a plain multiline `add_input_text`, with no syntax highlighting. On 2026-11-21 the user deferred highlighting until Dear PyGui ships a code editor widget, so don't build a workaround unasked. **Before proposing it again, or when bumping Dear PyGui, read the Syntax highlighting section of `.claude/notes/dearpygui.md`**, which has what was checked, the workarounds and their limits, and how the user wants it switched off.
- Dear PyGui redraws the whole viewport every frame, idle or not (vsync on, `wait_for_input` unset). So the app's GPU load is that redraw, not the loading indicator, and replacing the indicator with static text would save nothing.
  - `main()` therefore ends with `runRenderLoop()` instead of `dpg.start_dearpygui()`. It is the same `is_dearpygui_running()`/`render_dearpygui_frame()` loop, plus a sleep until the next frame is due, so the frame rate is capped at `config.frameRateMax`. That is 30, the user's choice on 2026-11-22. Don't go back to `start_dearpygui()`.
  - Animations in Dear ImGui are time-based, so the cap changes their smoothness, never their speed.
  - `wait_for_input=True` would stop the idle redraw entirely. But Dear PyGui can't be woken from Python, so changes made from the callback thread (results, errors, the indicator, the 1 s reverts) would stay unpainted until the next input event. Power saving with platform-specific wake-ups is not built, so don't add it unasked.
  - **Before changing either loading indicator, the render loop or the cap, read the Loading indicator section of `.claude/notes/dearpygui.md`.**
- On exit Dear PyGui saves window layout to `settings.ini` inside the package directory (`settingsFile`, wired up through `init_file`). The file is gitignored.
- `--debug` turns on several things:
  - DEBUG logging with timestamps (all logging goes to stdout). Modules log through their own `logger: logging.Logger = logging.getLogger(__name__)`, never through `logging.debug()` and friends (ruff `LOG015`). The `logging.basicConfig` call in `main()` configures the root logger they propagate to, and its format has no `%(name)s`.
  - A `tabulate` dump of each result. It is a deliberate `print`, not logging.
  - Tracebacks to stderr.
  - A Dev menu.
  - A prefilled SIMBAD input.
- The README's "Known problems" section covers six issues:
  - SIMBAD at CDS is unavailable since October 2026, and the mirror fallback.
  - Installation fails on a Python version too new for Dear PyGui's wheels. It ships no sdist, and on 2026-11-20 its wheels stopped at 3.14.
  - astropy contacts remote hosts at startup.
  - PyVO raises `UnicodeDecodeError` on non-ASCII results (#19).
  - Cloudflare's WAF blocks some valid queries to NASA Exoplanet Archive with a 403, and the app explains that in the error message.
  - NASA Exoplanet Archive's TAP service no longer accepts `WITH` and subqueries in `FROM` (its table-name check, not the Oracle database, rejects them), with the old `latestEntries` example query and its self-join replacement side by side.

  Its Platforms section says which platforms Dear PyGui 2.3 has wheels for.

## Conventions

- Functions and variables use camelCase (`executeQuery`, `lastQueryResults`), and module-level variables carry type annotations.
- Long strings are adjacent string literals inside parentheses (implicit concatenation), one fragment per line, each ending with the space that separates it from the next. Plain and f-string fragments mix freely, and an argument that is only the string needs no extra parentheses. `str.join` is only for runtime sequences (`".".join(map(str, …))`, `", ".join(oids.colnames)`). A fixed tuple of fragments trips ruff's `FLY002`, and inside a list or tuple the concatenation needs its own parentheses (`ISC004`). Example queries put an explicit `\n` at the end of each line.
- Imports come in three groups in this order: `# standard libraries`, `# 3rd-party dependencies`, `# own stuff`. Each group starts with its header comment and a bare `#` line, and a blank line separates the groups. ruff's `I001` enforces the sorting within each group. The headers of the 3rd-party and own groups survive sorting only because each is attached to the first import of its group. So a new import that sorts above that one has to be written directly below the header, otherwise `ruff check --fix` puts it above the header. This was verified on stdin. The first group's header is safe either way, because it's the file's leading comment.
- Python 3.12 is the minimum, so 3.12 syntax is fine (PEP 695 `type` statements, PEP 701 f-strings, parenthesized context managers). It is declared in five places that change together: `python_requires` and the classifier in `setup.cfg`, the README's Dependencies list, `target-version` under `[tool.ruff]` and `python-version` under `[tool.ty.environment]` in `pyproject.toml`. Ask before raising it further.
- The version has a single source, `__version_info__` in `version.py`, which `setup.cfg` reads through `attr:`. Since `2026.11.20` it is date-based: the release date as `YYYY.M.D`, with no zero-padding (1 February 2027 is `2027.2.1`), stored as `(YYYY, M, D)` ints. That is also what PEP 440 normalization would produce, since it drops leading zeros (versions up to and including `0.8.2` were 0.x.y). A release bumps it and adds a `changelog.md` section: `## YYYY.M.D`, then straight to the bullets. The version already is the date, so there is no ``Released on `YYYY-MM-DD`.`` line. Only the 0.x.y entries have one, and they keep it. The release commit is titled `Version YYYY.M.D`. Commits about an issue start with `Closed #N:` or `For #N:`.
- `README.md` and `changelog.md` carry MarkdownTOC blocks (a Sublime Text plugin) between `<!-- MarkdownTOC -->` markers. When you add or rename a heading, update the block by hand in its existing format.
- The git remote uses an SSH URL, so fetch and push don't work from the container. The only branch is `master`.
